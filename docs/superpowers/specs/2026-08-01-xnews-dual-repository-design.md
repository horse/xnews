# XNEWS 双仓库编辑与公开发布设计

## 1. 目标

XNEWS 采用两个职责完全分离的仓库：

- `horse/xnews-editorial`：私有编辑工程仓库，保存趋势原始数据、话题聚类、来源核验、风险提示、内部草稿和发布清单。
- `horse/xnews`：公开新闻仓库，只保存标准新闻化内容、栏目页面、日期归档和必要的方法说明。

最高级编辑原则：

> 趋势数据用于决定报道什么，不用于决定新闻怎样写。公开稿必须先是一篇独立成立的新闻。

## 2. 当前问题

现有公开稿把内部方法直接写进正文，主要表现为：

- 标题以“进入榜单”“占据某时段”“多个词同时上榜”为主要动作；
- 导语先列趋势词，再解释新闻事实；
- 正文频繁解释标签聚类、时间点、榜单机制和传播结构；
- 每篇文章重复统计制度；
- GetDayTrends、排名、主榜、补漏榜进入普通读者阅读路径；
- 为满足字数而补充泛化背景、抽象正反意见或社交媒体机制分析。

这些内容对编辑有用，但不属于公开新闻正文。

## 3. 仓库职责

### 3.1 私有仓库 `horse/xnews-editorial`

建议目录：

```text
xnews-editorial/
├── README.md
├── config/
│   ├── schedule.yml
│   ├── editorial-policy.md
│   ├── source-policy.md
│   └── public-style-guide.md
├── raw/
│   └── YYYY-MM-DD/
│       ├── 1000.json
│       ├── 1400.json
│       ├── 1800.json
│       ├── 2200.json
│       ├── 0200.json
│       └── 0600.json
├── topics/
│   └── YYYY-MM-DD/
│       └── TYYYYMMDD-NNN.yml
├── dossiers/
│   └── YYYY-MM-DD/
│       └── TYYYYMMDD-NNN.md
├── drafts/
│   └── YYYY-MM-DD/
│       ├── priority/
│       ├── standard/
│       └── briefs/
├── reviews/
│   └── YYYY-MM-DD/
│       ├── fact-check.md
│       ├── style-check.md
│       └── coverage-check.md
└── manifests/
    └── YYYY-MM-DD.json
```

私有仓库保存所有工程痕迹，包括：

- 五个代表时点与06:00补漏榜；
- 原始排名和抓取时间；
- 同一事件标签的合并理由；
- 话题首次出现、持续时间和跨时点情况；
- 来源URL、证据摘录和核验状态；
- 事实风险、法律风险和不确定信息；
- 用户反应样本，但不得把少量样本自动写成“多数舆论”；
- 标题候选、稿件等级、退稿原因和发布状态；
- 公开文章对应路径与发布记录。

### 3.2 公开仓库 `horse/xnews`

建议目录：

```text
xnews/
├── index.html
├── assets/
├── about.html
├── methodology.html
├── archive.html
└── YYYY/MM/DD/
    ├── index.html
    ├── overview.html
    ├── news/
    │   ├── article-a.html
    │   └── article-b.html
    └── briefs.html
```

公开仓库只保存：

- 新闻首页；
- 日期归档；
- 每条独立新闻；
- 晨间总览；
- 简讯页；
- 关于页与单独的方法页；
- 必要的公开来源链接。

公开稿中不显示内部话题ID、置信度、聚类理由、失败查询、编辑等级和时点权重。

## 4. 内部话题记录格式

每个话题使用唯一ID：

```text
TYYYYMMDD-NNN
```

示例：

```yaml
topic_id: T20260801-001
working_title: 日元汇率干预预期
source_tags:
  - 為替介入
  - レートチェック
  - NY連銀
  - 政府・日銀
snapshots:
  - nominal_time: "10:00"
    observed_at: "10:29"
    ranks:
      為替介入: 1
      レートチェック: 4
      NY連銀: 8
merge_reason: 同属美日当局可能干预日元市场的同一事件
category: economy
priority: lead
facts:
  - claim: 美国财政部通过纽约联储通知银行为潜在行动做准备
    source_url: https://example.com/source
    verification: confirmed
  - claim: 美国已经实际实施干预
    verification: unconfirmed
editorial_risks:
  - 不得把准备行动写成已经实施
  - 不得仅凭市场上涨推断政策已经落地
public:
  slug: yen-intervention
  status: published
  repository_path: 2026/08/01/news/yen-intervention.html
```

核验状态固定为：

- `confirmed`：由官方文件、一手声明或可靠媒体明确支持；
- `supported`：有多个可靠公开来源支持，但缺乏一手文件；
- `uncertain`：信息可能成立，但证据不足；
- `rejected`：经核验不成立或不应进入公开稿。

## 5. 每日时间制度

内部采集采用：

- 10:00：上午公共议题；
- 14:00：午后商业、游戏与机构发布；
- 18:00：白天议题与晚间内容的转场；
- 22:00：电视、体育、直播和娱乐黄金时段；
- 02:00：昨日主榜；
- 06:00：只检查重大突发和必须追加的凌晨事件。

第三方趋势站可能存在更新延迟，因此同时保存：

- `nominal_time`：代表时点；
- `observed_at`：实际读取时间；
- `source_timestamp`：网站自身显示的时间，若可取得。

公开文章不反复说明这些时点。完整制度仅在 `methodology.html` 介绍一次。

## 6. 编辑生产流程

```text
原始榜单采集
→ 标签规范化
→ 同一事件聚类
→ 建立话题档案
→ 来源检索与事实核验
→ 确定新闻价值和稿件形式
→ 编写内部事实稿
→ 新闻化重写
→ 事实检查
→ 语言与模板痕迹检查
→ 生成公开文件
→ 发布到 horse/xnews
```

### 6.1 选题规则

以下情况可以合并：

- 多个标签明显由同一节目、比赛、企业公告或事件触发；
- 人名、作品名和官方标签共同指向同一新闻；
- 同一事件在不同时间点使用不同表记。

以下情况不得仅因类别相近而合并：

- 两个不同角色的生日；
- 两家不同品牌的促销；
- 同一晚播出的不同电视节目；
- 不同球队的独立比赛，除非写的是联赛整体综述。

### 6.2 稿件类型

内部可使用以下等级，但公开页面不显示等级名称：

- `lead`：当天最重要的8—12个主题；
- `standard`：独立成立的普通新闻；
- `brief`：事实明确但信息量有限；
- `index-only`：含义无法可靠确认，仅保留在内部索引，不公开猜测。

字数是结果，不是硬性目标：

- 重点稿通常800—1500字，但信息完整时可以更短；
- 普通稿通常300—800字；
- 简讯通常80—250字；
- 不允许为达到字数补写无来源背景或空泛分析。

## 7. 公开新闻写作标准

### 7.1 标题

标题报道事件，不报道榜单。

禁止作为常规模板：

- “某词进入趋势”；
- “某标签占据上午榜”；
- “多个相关词同时上榜”；
- “某话题在五个时点持续出现”。

榜单表现只有在它本身构成新闻时才能进入标题，例如官方标签被恶意劫持、异常刷榜或重大传播事件。

### 7.2 导语

导语优先回答：

- 谁；
- 在何时；
- 做了什么或发生了什么；
- 为什么重要；
- 最新状态如何。

不得以一串标签作为常规第一段。

### 7.3 正文结构

默认结构：

```text
新闻事实
→ 关键细节
→ 必要背景
→ 最新进展或影响
→ X上的反应
```

X上的反应是报道的一部分，不是整篇文章的骨架。

### 7.4 用户反应

- 有明确公开帖子时，准确概括并保留来源；
- 只观察到有限样本时，使用“部分用户”“相关投稿中可见”等限定表达；
- 不得凭少量帖子写成“网友普遍认为”“舆论一致”；
- 不机械制造“有人支持、也有人反对”的伪平衡；
- 不把营销转发等同于自然讨论。

### 7.5 背景信息

只加入理解新闻所必需的背景。禁止：

- 为凑字数加入百科式介绍；
- 泛泛讨论行业周期、粉丝文化或社交媒体机制；
- 在每篇电视稿中解释“同步观看如何产生多个标签”；
- 在每篇生日稿中重复解释“角色生日是粉丝年度仪式”；
- 没有来源的宏大社会意义。

### 7.6 方法痕迹

以下词语和概念默认只属于内部稿：

- 主榜；
- 补漏榜；
- 五时点；
- 聚类；
- 置信度；
- 覆盖检查；
- 原始标签索引；
- 排名权重；
- 跨时点出现；
- 公开榜单重建版。

公开页面可在方法页说明数据限制，但不得在每篇文章底部重复。

## 8. 公开页面设计

### 8.1 首页

首页像新闻媒体，而不是项目仪表盘：

- 一个主标题；
- 主要新闻；
- 最新新闻列表；
- 分类入口；
- 日期归档；
- 不显示原始记录数量、聚类数量和工程状态。

### 8.2 日期页

日期页按新闻重要性和栏目组织，不显示“10篇重点、19篇普通、29条简讯”的生产统计。可以使用：

- 今日焦点；
- 社会与经济；
- 文化与娱乐；
- 游戏与动漫；
- 体育；
- 简讯。

### 8.3 文章页

文章页显示：

- 栏目；
- 标题；
- 导语；
- 正文；
- 发布时间与更新时间；
- 主要来源；
- 返回当日首页。

不显示趋势排名、话题ID和内部稿件等级。

### 8.4 方法页

`methodology.html` 单独说明：

- XNEWS为什么关注趋势；
- 五个代表时间点；
- 数据可能存在延迟；
- 趋势不等于民意；
- 品牌活动和自然讨论如何区分；
- 更正政策。

方法页不进入新闻正文。

## 9. 现有2026年8月1日内容迁移

现有公开内容作为内部事实底稿使用，但不直接保留为最终公开稿。

迁移顺序：

1. 建立私有仓库结构；
2. 将六个时点原始榜单和300条记录迁入 `raw/2026-08-01/`；
3. 为现有话题建立内部YAML档案；
4. 把现有29篇文章拆成事实、背景、反应和方法痕迹；
5. 先重写三篇风格基准稿：
   - 日元干预；
   - キオクシア；
   - 月末插画；
6. 审核三篇是否达到“像新闻”的标准；
7. 按同一标准重写其余重点稿和普通稿；
8. 将不可靠的简讯降为内部索引，不在公开版猜测；
9. 重做首页、日期页、关于页和方法页；
10. 删除公开仓库中不再使用的工程化页面与旧稿。

## 10. 三篇基准稿的风格目标

### 日元干预

- 标题聚焦日元变化与美方准备行动；
- 导语说明消息来源、市场反应和未确认事项；
- 趋势词仅在后文说明此事在日本X引发关注；
- 不把准备干预写成已经干预。

### キオクシア

- 标题聚焦财报、回购、拆股或股价反应；
- 使用公司公告中的具体数字；
- 区分事实、分析师预期和投资者情绪；
- 删除关于“多个财经词共同上榜”的方法分析。

### 月末插画

- 作为文化或网络生活短稿；
- 先写创作者在月末集中发布作品；
- 再写常见投稿形式和参与者反应；
- 不写“进入晚间榜”“固定标签说明社群机制”等工程化结论。

## 11. 发布接口

私有仓库生成 `manifests/YYYY-MM-DD.json`，列出公开稿：

```json
{
  "edition_date": "2026-08-01",
  "articles": [
    {
      "topic_id": "T20260801-001",
      "slug": "yen-intervention",
      "title": "日元急升，美方被曝为潜在汇市干预做准备",
      "category": "economy",
      "status": "publish",
      "public_path": "2026/08/01/news/yen-intervention.html"
    }
  ]
}
```

公开仓库不读取私有仓库的全部内容，只接收经过审核的最终新闻正文与必要元数据。

## 12. 更正与审计

- 事实更正首先记录在私有话题档案；
- 公开稿更新时标记更新时间；
- 重大错误在文章中添加简短更正说明；
- 内部保留修改原因、旧说法和来源变化；
- 不因趋势热度高而降低事实核验标准。

## 13. 验收标准

双仓库改造完成后应满足：

- 公开首页和文章页不出现工程术语；
- 任意一篇文章脱离X趋势背景仍可独立阅读；
- 标题和导语首先报道事件；
- 每个公开事实都可追溯到私有档案中的来源；
- 原始榜单、排名、聚类和风险记录只存在于私有仓库；
- 公开稿没有统一的“标签上榜—用户讨论—趋势意义”模板；
- 三篇基准稿通过人工阅读后，才批量重写其余内容。
